# TrendIt 다음 작업 상세 계획

2026-10-23 상태: 아래 1~5의 화면·API 연결은 완료했고, 후속 코드·보안 검사와 누락 동작 수정까지 진행했다. [화면 연결 결과](experiments/UI_INTEGRATION_20261022.md), [최신 품질 점검](experiments/QUALITY_SECURITY_20261023.md) 참조. 아래 내용은 수립 당시 기준의 계획으로 보존한다. 6의 추가 모델 실험은 아직 실행하지 않았다.

목표는 검증한 T0 분류 모델을 실제 화면에서 같은 의미로 사용할 수 있게 만드는 것이다. 우선 예측 화면·모델 성능 화면·오류 처리를 완성하고, 추가 성능 실험은 그 다음에 진행한다.

## 1. 입력·결과 기준 확정

현재 `PredictionPage.jsx`는 조회수·댓글·요일·시간을 `/predict/preview`로 보낸다. 새 모델에는 최초 진입 시각, 발행 시각, 최초 진입 순위가 추가로 필요하다. 시간과 순위를 임의의 기본값으로 채워 연결하지 않는다.

| 입력 | 처리 기준 |
|---|---|
| 최초 차트 진입 시각 | KST로 입력·표시하며 API에는 타임존을 명시 |
| 영상 발행 시각 | 진입 시각 이전이어야 함. 요일·시각·진입 지연은 서버에서 파생 |
| 최초 진입 순위 | 1~200 정수 |
| 진입 당시 조회수·댓글 | 0 이상 정수. 현재 누적 통계로 대체하지 않음 |
| 카테고리 | 상태 API가 제공한 학습 범위 5개만 선택 가능 |

응답은 실험 ID, 모델, TDI v2 대상, 모델 점수, 판정, Validation 선택 임계값으로 구성한다. 점수를 정답률·교정된 확률·신뢰구간으로 표현하지 않는다. TDI 정답 기준 0.4와 모델 판정 임계값을 구분한다.

완료 기준: 필수값이 없으면 제출할 수 없고, 미지원 카테고리·음수·소수 건수·잘못된 날짜는 구체적 입력 오류로 표시한다.

## 2. 예측 화면의 실제 모델 연결

주요 대상: `frontend/src/pages/PredictionPage.jsx`, `frontend/src/styles/PredictionPage.css`, 입력·결과 매핑 도우미.

- 기본 화면을 검증된 T0 분류 흐름으로 구성한다. 24h 모드는 검증 범위가 정리될 때까지 현재 모델의 기능으로 제공하지 않는다.
- 입력 전 결과는 비워 두고, 샘플은 입력값을 채우는 용도로만 제공한다. API가 실패하면 임의 예측을 만들지 않는다.
- 기존의 72.4%, 221.8시간 등 고정 예시 결과와 휴리스틱으로 만든 기여도 비율을 제거한다.
- 분류 모델이 출력하지 않는 예상 지속 시간·정확도·신뢰구간은 결과 카드에 표시하지 않는다.
- 결과는 실제 응답의 모델 점수와 임계값으로 판정한다. 임의의 High/Medium 기준을 새 모델에 덧씌우지 않는다.
- 결과 옆에 해당 요청의 입력 요약을 남긴다. 요청 중 입력이 바뀌거나 오래된 응답이 도착해도 다른 입력의 결과로 오해하지 않게 한다.
- 모델 준비 안 됨, 입력 오류, 연결 실패, 시간 초과를 구분하고 재시도할 수 있게 한다.

완료 기준: 화면에 보이는 값이 같은 입력의 API 응답과 일치하며, 실패·대기 상태에서 결과를 정상 예측처럼 표시하지 않는다.

## 3. 성능 표와 버전의 출처 통일

주요 대상: 모델 페이지·`ModelInterpretPage.jsx`·`mlProjectData.js` 등 성능 상수 사용 지점, 새 평가 요약 API.

- 검증된 실험 보고서에서 선택 모델, Validation/Test 지표, 표본 수, 분할 기준과 제한을 읽는 평가 요약 API를 만든다.
- 화면에 남은 과거 AUC 0.895·0.9111 등의 값을 현재 성능처럼 노출하는 경로를 정리한다.
- 기본 화면은 현재 v2 실험을 사용한다. 과거 결과를 보존할 때는 실험 시점·데이터·평가 조건이 다른 기록임을 분명히 한다.
- 지표를 불러오지 못하면 사용할 수 없음을 표시한다. 임의 기본 성능을 채우지 않는다.
- 모델 선택은 Validation 기준이었다는 사실과 단일 분할·시드의 제한을 함께 전달한다.

완료 기준: README·평가 API·화면이 같은 실험 ID와 수치를 가리킨다.

## 4. 실시간 영상 목록의 연결 범위 결정

`VideoPage.jsx`는 현재 조회수와 화면 순서를 초기값처럼 전달할 수 있다. 현재 순위를 최초 진입 순위로, 현재 조회수를 최초 관측 조회수로 취급하면 학습 시점과 의미가 달라진다.

- 이번 v2 연결은 정확한 초기 관측을 제공하는 예측 화면부터 진행한다.
- 최초 관측 자료가 없는 실시간 영상에는 v2 검증 성능을 적용한 점수라는 표현을 사용하지 않는다.
- 영상 목록을 v2와 연결하려면 별도로 최초 진입 시각·순위·조회수·댓글을 저장하는 수집 기준과 출처가 필요하다. 이 수집 기능은 별도 작업으로 분리한다.

완료 기준: 과거 관측 분류와 현재 영상 분석이 같은 검증을 받은 기능처럼 보이지 않는다.

## 5. 실제 브라우저 검증

문자열 존재 검사 대신 다음 사용자 동작을 실행해 검증한다.

1. 샘플 입력 → 제출 → 실제 API 결과와 화면 점수·판정·실험 ID 일치.
2. 날짜·숫자 오류 → 제출 차단 또는 해당 필드 오류 표시.
3. API 503·연결 실패·시간 초과 → 임의 결과 없음, 재시도 가능.
4. 중복 클릭·입력 변경·늦은 응답 → 결과와 입력의 연결 유지.
5. 새로고침·모바일 화면 → 입력·오류·결과를 읽고 조작할 수 있음.
6. 모델 보고서 로딩 실패 → 과거 성능이나 고정 숫자로 대체하지 않음.

검증 산출물: 프론트엔드 빌드, 동작 테스트, 핵심 흐름 스크린샷과 재현 방법. 실제 API를 사용하는 성공 흐름과 오류를 주입한 실패 흐름을 구분한다.

## 6. 그 다음의 근거 강화

- 저장된 Test 예측으로 같은 영상의 여러 이벤트를 묶어 재표집해 AUC·F1와 모델 차이의 오차 범위를 추정한다. 이 분석으로 현재 선택 모델을 사후 변경하지 않는다.
- 고정한 설정으로 시드를 달리해 학습 변동을 확인한다. 변경 기준은 실행 전에 정한다.
- 과거 기간을 바꾼 평가는 안정성 분석으로 보고한다. 완전히 새로운 기간의 검증은 별도의 미사용 자료를 확보한 뒤 진행한다.
- 필요하면 반복 영상에 대한 별도 평가를 만든다. 현재의 새로운 영상 평가와 섞지 않는다.

현재 단계의 우선순위는 1~5다. 목표는 예측이 실제 화면까지 정확한 의미로 이어지고, 공개된 근거와 표시가 일치하는 상태다. 작업은 현재 VS Code·WSL·CPU 환경에서 진행할 수 있다.
