## 3. 질문이 나올 때 함께 설명할 내용

- **왜 선택 모델의 Test AUC가 가장 높지 않은가?** Validation AUC 0.823683으로 선택했다. LightGBM의 Test AUC 0.814206이 선택 모델 0.812765보다 높지만, Test를 보고 교체하면 Test가 선택 자료가 된다. 근접 차이의 통계적 우위도 검증하지 않았다.
- **AUC 1.0에서 0.8128로 떨어졌는데 개선인가?** 누수가 있던 수치를 폐기하고 실제 사용 시점의 입력으로 재평가한 것이다. 성능 향상 근거는 같은 v2 조건의 기준 모델 비교로 제한한다.
- **0.4860은 성공 확률 48.6%인가?** 모델 출력 점수다. 개별 점수의 확률 교정·신뢰도를 검증하지 않아 성공 확률로 설명하지 않는다. 성능 지표의 재표집 구간과 구분한다.
- **고지속 기준은 무엇인가?** 지속 시간을 Train의 카테고리 q95로 정규화한 값과 최고 순위 가중치의 곱인 TDI v2 ≥ 0.4다. 단순히 24h/48h 이상 남는다는 고정 시간 기준이 아니다.
- **오탐은 얼마나 남았나?** 선택 임계값에서 TN 2,103 / FP 1,188 / FN 258 / TP 1,437. Precision 54.74%, Recall 84.78%다. 고지속 후보 판정 중 약 45.26%는 오탐이므로 광고 자동 집행 근거로 쓰기 어렵다.
- **개인 MLP의 구조는?** 수치 9개와 카테고리 embedding 3차원, 은닉층 256→128→64, BatchNorm/ReLU/Dropout 0.3, skip 연결, BCEWithLogitsLoss와 AdamW. 실제 코드와 학습 범위를 보고 설명한다.
- **왜 RunPod를 쓰지 않았나?** 이 규모의 공통 비교와 화면·API 검증은 현재 CPU/WSL 환경에서 실행됐다. 대규모 GPU 학습 비용이나 속도 절감률을 측정한 것은 아니다.

## 4. 기여 범위와 아직 주장하면 안 되는 내용

기존 팀 역할에서 김은진의 담당은 공동 전처리와 개인 MLP/TabNet 실험이다. 기존 DB·머신러닝·프론트엔드/백엔드는 팀원별 담당이 있었다. [README의 역할 표](../README.md)를 기준으로 기존 팀 구현, 개인 실험, 이번 보완 작업을 구분한다. 이번 변경 파일과 검증 근거는 [구현 보고서](experiments/UI_INTEGRATION_20261022.md)에 연결했다.

현재 근거로는 다음을 성과로 쓰지 않는다.

- 기존 AUC 1.0/0.895/0.9111을 현재 운영 성능으로 표기하거나 새 AUC와 직접 비교.
- 정확도 99%, 매출·CTR·광고 ROI 개선, 실제 고객 사용, 운영 장애 감소율, GPU 비용 절감률.
- 다른 기간·장비의 일반화, 5시드 변동이나 조건부 재표집 구간을 넘는 통계적 보장. 추가 진단의 실행 범위 안에서만 설명한다.
- 실시간 T0 수집, 지속 시간 회귀·24h 업데이트, SHAP 기여도·인과관계가 구현·검증됐다는 주장.
- 팀 전체 구현이나 도구 지원을 받은 보완 전부를 과거의 개인 단독 개발로 서술.

## 5. 현재 해결 상태와 남은 기술 과제

전체 lint 35/1→0/0, npm 경고 10→0은 유지했다. 후속으로 주요 분석·홈·대시보드·캠페인의 고정 수치와 출처 혼합을 정리했고, 5시드 변동·영상 단위 재표집·독립 설치 재현을 수행했다. [최신 결과](experiments/FOLLOWUP_RESULTS_20261023.md)와 [기계 판독 근거](experiments/followup_verification.json)를 기준으로 설명한다.

- 기준 시드 42 모델·임계값 0.44와 Test AUC 0.8128/F1 0.6653은 유지한다. 5시드 평균은 새로운 모델의 성능 향상 수치가 아니다.
- 재표집의 Logistic 대비 AUC·F1 차이 구간은 양수지만 Recall 차이는 음수다. 모든 지표가 좋아졌다고 쓰지 않는다.
- 같은 시간 분할의 5시드 변동과 고정 모델의 영상 재표집은 외부 기간 검증·확률 교정·운영 광고 효과를 대체하지 않는다.
- HTTP 테스트 도구 경고 1개, 재학습의 비선택 sklearn MLP 수렴 안내·TabNet 실행 안내는 원시 로그에 남겼다.
- 외부 YouTube/DB 운영·실시간 T0 수집·공개 서비스 배포·다른 OS와 실기기 검증은 별도 범위다. 미산출 중요도·클러스터 검정은 예시로 채우지 않는다.
- 개인 포크 main에 직접 반영하는 방식을 사용한다. PR은 만들지 않으며 최신 push·원격 검사 상태는 [마감 기록](experiments/CLOSURE_RESULTS_20261102.md)에서 확인한다. 서비스 배포는 별도 범위다.

## 6. 증거를 다시 찾는 방법

1. 현재 API·문서·원격 결과는 [최신 마감 기록](experiments/CLOSURE_RESULTS_20261102.md)에서 확인한다. 이전 [품질·보안 검증](experiments/quality_security_verification.json)과 [실제 로그·소스 해시](experiments/quality_evidence/)에서 이번 해결 근거 확인.
2. [모델 수치의 원본 보고서](experiments/t0_v2_report.json)와 [검증 JSON](experiments/ui_integration_verification.json)에서 실행 ID·원시 수치·파일 해시 확인.
3. [화면 연동 구현 보고서](experiments/UI_INTEGRATION_20261022.md)에서 테스트 재현 절차와 실제 API/오류 주입 구분 확인.
4. [원시 증거 폴더](experiments/ui_evidence/)에서 로그·실제 응답·화면 캡처·변경 전/후 소스 해시 확인.
5. 실제 코드 설명은 저장소의 학습·입력 계약·추론·API·화면 소스를 기준으로 하고, 보관한 화면 이미지를 실행 결과의 보조 증거로 사용.

모든 수치는 특정 데이터·분할·시드·코드 상태의 결과다. 최신 작업으로 수치가 달라지면 기존 기록은 남기고 새 실행 ID와 비교 조건을 추가한다.
